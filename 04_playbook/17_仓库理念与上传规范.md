# 仓库理念与上传规范（v1.0 · 2026-11-22）

> **这份文件回答两个问题：为什么做这个仓？往这个仓里放什么？**
> 它排在《纪律》之前——先知道为什么要做，再谈怎么做。
> 任何人（含智能体）在开工前读完这一份，再按 `README.md` 的必读顺序读下去。
> 与本文冲突的任务书、旧习惯，以本文的目标与边界为准；确实要破例，在工程报告里写明理由。

## §1 理念：把数学搭成一个「可执行、可对齐」的沙盒

这个仓最初是**翻译仓**：把散落、绝版、只有日文/法文/俄文的中文数学文献译成中文，让普通读者读得到。
这件事继续做，但它已经不是全部，也不是最重要的部分。

我们真正想搭的东西，是一个**像 coding 的沙盒那样的数学工作台**：

- 写代码的人有一个沙盒：代码写下去，编译器当场告诉你对不对，测试当场跑给你看，错了就改，改完再跑。
  数学目前没有这样的沙盒——论文写下去，只有同行几年后才发现某一步不成立。
- 我们要给中文数学补上这个沙盒的**底座**：**(a)** 每一段译文都能对应回原文的一页一行；**(b)** 每一个术语、记号都有唯一、可机器引用的登记；**(c)** 每一条定理陈述都有同一句话的自然语言版本与形式语言（Lean 4）版本；**(d)** 上面三条都被脚本检查，不是靠人记得。

这件事的目标不是「让模型做更多数学题」。**我们关心的是模型能不能真的推理**：读懂一条陈述、拆出它的前提、找到它依赖的定义、在证明里定位错误、把一处修改传播到所有引用它的地方。数学只是目前**最便宜、最严格、反馈最干净**的训练场——因为对错不由人说了算。

自然语言与形式语言的对齐，是让这件事**可验证**的使能条件：自然语言那一侧给出"这句话在中文里是什么意思"，形式语言那一侧给出"这句话在 Lean 里是什么意思"，两边必须逐条咬合。咬合上了，模型学到的不是"数学知识"，而是"把模糊的话逼成精确的话"的能力——这种能力可以搬去任何领域。

所以这个仓的产出有三层，重要性从低到高：

| 层 | 产出 | 服务的对象 | 重要性 |
|---|---|---|---|
| 1 | 可读的中文译注本 | 人（学生、研究者） | 基础，但不终点 |
| 2 | 术语/记号规范、资料卡、语料 | 机器可读的结构化底稿 | 中间层 |
| 3 | **自然语言 ↔ 形式语言的对齐卡（Lean 4）** | 模型推理能力的训练与评测 | **本仓的重心** |

一句话版本：**页数是库存，对齐才是产能。**

## §2 这个仓里有什么（五层资产）

| 层 | 位置 | 是什么 | 谁在用 |
|---|---|---|---|
| 底本层 | `08_source_code/<编号>/源码/` | 原文与译文的 LaTeX 源、插图、页面图像 | 译者、校对 |
| 译注层 | 同上 + `工程文件/deliverable/` | 成品 PDF、译注、页码对照 | 人 |
| 语料层 | `01_corpus_zh/` | 段落级中英对照语料、术语基、数语规范四表 | 检索、训练、术语收敛 |
| 卡片层 | `datasets/<集>/cards/` | 概念卡/定理卡/推导卡/对齐卡（JSON，带来源与状态） | 模型、评测 |
| 对齐层 | `datasets/leanstmt/` + `01_corpus_zh/数语规范/STYLE_FORMAL.md` | NL↔Lean 陈述对齐、toolchain 与 mathlib 版本钉死 | 形式化、推理训练 |

规则：**上层只能引用下层的登记项，不能绕过它另造一套。** 术语只能来自 `TERMS.tsv`/termbase，记号只能来自 `SYMBOLS.tsv` 或本工程 preamble，陈述只能来自资料卡 01/03 或已复核的卡片。

## §3 该往这个仓上传什么

### 3.1 一定要传（一个工程算"完成"的最低配置）

| 项 | 位置 | 要求 |
|---|---|---|
| BRIEF | `工程文件/BRIEF.md` | 书目、底本、页数、结构页表、翻译决定、状态勾选 |
| STYLE_GUIDE | `工程文件/STYLE_GUIDE.md` | 本书的文体/术语/公式/译注约定（可继承 `STYLE_NL.md`，只写差异） |
| 术语表 | `工程文件/work/glossary.tsv` | english / 中文 / 等级 / 依据；完工后并入 `termbase.jsonl` |
| 译文源 | `源码/main.tex` + `源码/chunks/*.tex` | 能独立编译；不依赖译者本机路径 |
| 成品 | `工程文件/deliverable/*.pdf` | 与源同步；文件名带书名与版本 |
| 资料卡 | `资料卡/00-速览.md` … `04-术语文献勘误.md` | 五件套；01/03 必须能支撑对齐卡抽取 |
| 登记 | `RELEASE_REGISTER.csv` 一行 + `03_translations_meta/<编号>/` | 底本类型、权利、页码、直链 |
| 统计 | 不动 | `make_stats.py --write` 自动汇总，不要手改数字 |

### 3.2 可以传（有价值，但要标注状态）

- **草稿/半成品**：放 `工程文件/work/`，文件名带 `draft`/`WIP`，在 BRIEF 状态里写明"未复核"。
  仓库允许草稿存在，但不允许草稿冒充成品。
- **过程记录**：通读笔记、疑点清单、审校批注、diff 报告——放 `工程文件/work/` 或 `reports/`。
- **页面图像**：`工程文件/work/pages/pNNN.png`（公式核对用）。单页 ≤ 400 KB，整书 ≤ 200 MB；超过就只留抽样页。
- **大文件**：单文件 > 50 MB 一律走 Release 附件，不放进 git；在 `_PDF清单.tsv` 里写直链。
- **思考链**：只有通过 `09_thinking` 硬纪律（R1–R12）并过 `tools/thinking_audit.py` 的才进 `09_thinking/`。

### 3.3 绝对不传

| 不传 | 原因 |
|---|---|
| 未经授权的出版社 PDF/扫描件（在版图书全文） | 版权；只传自产译文与元数据，底本只在本地 |
| 会话原始分片（`.jsonl` 未脱敏） | 含个人信息、路径、密钥风险；只传 `06_sessions_raw/_attachments.json` + 脱敏后的样本 |
| 密钥、token、cookie、账号文件 | 任何情况下 |
| 中间产物垃圾：`__pycache__`、`*.aux/*.log/*.out/*.toc`（成品工程可留一份 log 作证）、`*.synctex.gz` | 体积与噪音 |
| 本机绝对路径写进正文 | 换机器就断；路径只出现在 `工程文件/work/` 的说明里 |
| 未复核的"结论"当事实写进 README/DATASHEET | 统计口径只认 `_meta/stats.json` |
| `CON`、`NUL` 之类 Windows 保留名生成的设备文件 | MSYS 误建，永远不要提交 |

### 3.4 判定口诀

> **能被人复核的留下；只能被自己相信的别留；能重跑的不要存结果，存命令。**

## §4 每次开工必做（检查清单）

开工前，按顺序做这五件事，做完才能动笔/动脚本：

1. **读本文 §1**（30 秒）：确认这次要做的事落在哪一层（译文/语料/规范/卡片/对齐）。
2. **读本工程 `工程文件/00_开工必读.md` + `BRIEF.md` + `STYLE_GUIDE.md`**：知道这本书的底本、页数、已有决定。
3. **读 `04_playbook/01_数学文献翻译纪律.md` 的相关节**：整书翻译读 §0–§4；只做卡片读 `datasets/README.md` §4–§5。
4. **查现状**：`git status`、`python make_stats.py --check`（数字是否漂移）、本工程 `工程文件/work/` 有没有上一轮的疑点清单。
5. **写任务卡**：这次要改哪些文件、判定"做完"的标准是什么、要不要更新 BRIEF 状态。任务卡放 `工程文件/work/`，文件名 `TASK-YYYYMMDD.md`。

收工时同样五件事：跑测试（见 §5）→ 更新 BRIEF 状态 → 更新 CHANGELOG → `make_stats.py --write`（若动了实物）→ 提交（提交信息写清"改了什么、为什么"）。

## §5 三道闸门（提交前必跑）

```bash
python make_stats.py --check        # README 统计块与实测一致
python tools/check_numbers.py       # 全仓无退役数字
python tools/build_norm.py --check  # 数语规范四表与源表一致
```

按改动类型加跑：

| 改了什么 | 加跑 |
|---|---|
| 卡片 JSON | `python tools/ds_lint.py`、`python tools/entry_lint.py` |
| 台账/登记 | `python tools/check_compliance.py` |
| 大文件/清单 | `python tools/check_manifest.py` |
| Lean 对齐卡 | `lake build`（在 `datasets/leanstmt/lean/ShuyiFormal/` 的孪生工程里）|
| 站点 | `python tools/build_site.py`（站点从 `_meta/stats.json` 取数，不要手改 `site/`）|

## §6 目录与命名

- 工程目录：`08_source_code/<主题编号>-<序号>_<中文题名>`，题名里的括号用全角。
- 主题编号：SY01 镜像对称、SY02 几何朗兰兹、SY03 量子场论、SY04 弦论、SY05 辛几何/拓扑、SY07 其他几何、SY08 双有理、SY99 专题。
- 数据集：`datasets/<短名>/`，短名小写、无空格；卡片 `cards/<type>/<id>.json`，id 与文件名一致。
- 对齐卡：`datasets/leanstmt/cards/statements/<track>-<s|g><NN>.json`（s=certified，g=gap）。
- 中文与拉丁字母之间不留空格（`Koszul 对偶` 这类"人名+汉字"从既有习惯保留一个半角空格，见 `数语规范/README.md` §3）。
- 文件名不用日期，除审计/评估报告（`AUDIT_YYYY-MM-DD_*.md`）。

## §7 什么叫"一个工程算完成"

不是"PDF 编译出来了"，而是下面七条全绿：

1. 译文能独立 `xelatex` 三遍、无 error、目录与交叉引用正确；
2. 术语表并入 termbase，`build_norm.py --check` 通过，无新增一外多中冲突（或已裁定并记录）；
3. 资料卡五件套齐全，01/03 的每条都带原文页码；
4. 至少 1 条对齐卡（certified 或带 gap 说明），进 `index.jsonl`；
5. `RELEASE_REGISTER.csv` 与 `03_translations_meta/` 登记完整，合规检查无 error；
6. BRIEF 状态勾完，CHANGELOG 有一条"完成了什么、留下了什么"；
7. `make_stats.py --write` 后数字一致，提交信息可读。
