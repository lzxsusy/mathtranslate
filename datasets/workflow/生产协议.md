# 数据集生产协议 v0.1

> 配套：[../README.md](../README.md)、[../schema/](../schema)、`tools/ds_lint.py`。
> 目的：把「翻译」这件一次性的活，拆成可复制、可审校、可评测的数据生产线。

## 0. 角色

| 角色 | 职责 | 产出 |
|---|---|---|
| 选段员 | 从工程源码挑单元、定对齐粒度 | `select.tsv`（pkg / file / 行区间 / 页 / 原文页） |
| 译者（生产） | 写译文片段、`why`、`choices`、术语 | `parallel/` 草稿 |
| 精读员 | 写 claim / 骨架 / 补步 / 易错点 | `deepread/` 草稿 |
| 标注员 | 标高光、难证、枢纽段 | `highlights/` |
| 审校 | 逐条核对数学与中文，改 `status` | `reviewed_by` 两人签名 |
| 评测员 | 出 held-out 题、写 rubric、盲测 | `bench/` |

一人可以兼多角，但**同一条记录的 `status` 不能由写它的同一个人单独从 draft 提到 published**。

## 1. 选段规则

1. 优先选：定义了全文关键对象的段落、跨节复用的构造、作者自己标了 `less evident / surprising` 的地方、脚注里藏了技术限定的地方。
2. 不选：纯引用列表、纯排版说明、无数学内容的过渡句。
3. 粒度：一句到三句；公式块整体算一个单元。
4. 每条记录必须能独立读懂：`context` 里给上一句的话题。

## 2. parallel：原文片段 + 译文 + 为什么

提示词模板（生产）：

```
你是数学翻译的「译法记录员」。给你原文片段（EN）与已定译文（ZH），
不要重译，只做三件事：
1) 逐句对齐，标出中文的断句/合并/语序调整；
2) 写 why：这条调整解决了什么中文阅读问题（歧义、悬置、指代、节奏）；
3) 给 choices：至少一个被拒译法 + 拒的理由（术语、语气、数学含义）。
硬约束：src_text 与 zh_text 各 ≤ 600 字；不得粘贴整段/整节；不引用未公开的书籍原文。
输出 JSON，符合 datasets/schema/parallel.schema.json。
```

审校清单：

- [ ] 原文引用与 arXiv 版本一致（vN 写明）；
- [ ] 译文与仓库 TeX 完全一致（逐字，含标点）；
- [ ] `why` 解释的是「为什么这样译」，不是「这段在讲什么」；
- [ ] 至少一条 `choices`，且被拒译法不是稻草人；
- [ ] 术语与 `01_corpus_zh/termbase.jsonl` 的裁决一致；不一致时在 `notes` 说明。

## 3. deepread：精读卡

提示词模板：

```
你是数学讨论班的主讲人。只给中文译文与原文页码，产出精读卡：
- claim：一句话说清这段建立了什么（可被复述、可被反驳）；
- proof_skeleton：3–8 步，每步一个动作（构造/引用/估计/取商）；
- gap_filling：原文跳过、但读者必须补的步；写清「补什么」与「怎么验」；
- pitfalls：2–4 个真实会犯的错（不是「注意符号」这类空话）；
- evidence：file:line 或 arXiv 页码，必须可点开。
不知道的写 confidence=low，不许编。
```

审校清单：

- [ ] `claim` 不是目录式复述（「本节讨论……」不算）；
- [ ] 每个 `gap` 都真的在原文里缺失，而不是自己没读懂；
- [ ] `how_verified` 写的是验证方式（算过/查过/引用），不是「已确认」；
- [ ] `pitfalls` 至少一条来自本工程的真实译校记录。

## 4. highlights：高光与难证

只收三类位置：

1. `brilliant_argument`：原文两三句话，但补全需要三到五步推理；
2. `hard_proof`：技术难点集中、跨节引用多、或作者自己省略了关键估计；
3. `structural_pivot`：后面所有节都挂在它上面的枢纽断言。

`why_hard` 必须回答「难在哪一步」，`strategy` 必须回答「怎么破」，两句都不能是「这很重要」。

## 5. traces：事件级工作流

数据来源：DSH 会话导出（`sessions_plain.jsonl` 消息 + `sessions_tools.jsonl` 工具事件）。

转换规则：

1. 一条 trace 对应一个可独立复述的任务单元（一节、一块、一次修编译）；
2. 事件映射：`read → read`，`write/edit → write`，`pwsh/python 校验 → check`，`报错后 edit → fix`，`team_task_* / 决策 → decide`；
3. `args_digest` / `result_digest` 各 ≤ 500 字，保留命令与关键输出，删掉无关列表；
4. 路径一律 `<path>`，邮箱/口令/私钥一律删除；
5. `fidelity`：直接从导出转录的写 `event`；事后按记录重建的写 `reconstructed`，并在 `source` 写明依据。

一条好 trace 的标准：读者能照着复现同样的步骤，包括那次失败。

## 6. bench：held-out 评测

- 题目只能来自 `parallel/`、`deepread/` **未收录**的段落；
- 每题至少 2 条 rubric，权重和 = 1；
- `must_not_include` 写「常见错误答案里的关键词」，用于自动扣分；
- 出一批题后先盲测 3 个模型，难度分布不合格就重出；
- `bench/` 不进训练集；发布时单独给 test 划分。

## 7. 批次与成本

一个「单元」= 一节（约 5–15 段）。经验成本（单人 + 单模型）：

| 产出 | 每单元条数 | 每条耗时 | 主要成本 |
|---|---|---|---|
| parallel | 6–10 | 3–5 min | 写 `why` 与 `choices` |
| deepread | 3–5 | 6–10 min | 补步与验证 |
| highlights | 2–3 | 5 min | 判断「难在哪」 |
| bench | 3–5 | 4 min | 出题与 rubric |

扩量顺序：arXiv 工程（37 部）→ 讲义（22 部）→ 学位论文（6 部）→ 图书只进 `_internal/`。

## 8. 发布前检查

```bash
python tools/ds_lint.py datasets/          # 0 错误
python tools/ds_publish.py --check         # 权利过滤（book 不出公开目录）
```

公开目录只允许 `rights: self` 与已确认许可的 `arxiv:*`；`book` 与未确认的 `arxiv:*` 记录留在 `_internal/`，永不进 git。
