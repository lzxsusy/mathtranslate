## 0. 一句话结论

这个主意**成立**，而且比“继续多翻几篇”更接近你真正想要的东西；但**不能按“把文章切给几个 agent，各写一章笔记”直接做**——那样只会得到一份拼盘式的读书报告，既不可核查，也不产生新理解。

可行的做法是：把每篇文章做成一个**有地图、有证据、有质询、有综合、有审计的 AI 研讨班**，产出不是“聊天记录”，而是一套可独立阅读、可逐条核查、可被网站复用的**研读档案**（seminar dossier）。

网站**可行**，但必须做版权分层：公开站只放你自己的导读、论证图、问题集、术语表与短引用，**不放整本译文的全文**；全文译本留在本地/私有层。最小可行版本不是先搭平台，而是**先用 JP11 这一篇 25 页的讲义，做出一个完整的研讨班页面并上线**。

## 1. 问题定义：翻译解决了什么，没解决什么

### 1.1 翻译工程已经解决的部分

你的「学术翻译总纲」已经把“把外文文献变成可信中文文本”这件事工程化了：

- 编号制、主题域、状态机、登记表；
- 八步生产流程（立项→抽取→样板章→分块并行→双校→编译审计→七件套→归档）；
- G1–G7 质量闸门；
- 多智能体写作用域互斥、术语冻结、单块 ≤8–10 页；
- 63 项已交付、约 6250 页的存量，以及 18 份待译公开 PDF、438 页的待办池。

这套体系解决的是**“文本层”**：原文说了什么，中文怎么说，公式有没有抄错，编译是否干净。

### 1.2 翻译没有解决的部分

一篇文献翻译完，仍然留下五个空缺：

1. **理解层**：这篇文章的核心问题是什么？论证链如何成立？哪些是定义、哪些是定理、哪些是作者的解释或猜测？
2. **校验层**：译本是否忠实？原文的省略、笔误、含混处，读者是否知道？公式与页图是否逐符号核对过？
3. **连接层**：这篇文章与同主题的其他文献是什么关系？它在你的 10 个主题域里处于什么位置？前置是什么、后续是什么？
4. **复用层**：这些理解能否变成可检索、可引用、可教学的资产（术语、论证图、问题集、习题、开放问题）？
5. **公共层**：能否形成一个对外的“文库/研讨班”站点，而不是一堆散落在桌面的 PDF？

“翻完就可以了”之所以不成立，是因为**翻译只完成了“可读”，没有完成“可懂、可查、可用、可传”**。

### 1.3 为什么“分章给 agent 各写报告”不够

这是本计划最需要说清楚的一点。naive 做法有六个结构性缺陷：

| 失败模式 | 表现 | 后果 |
|---|---|---|
| 无共同问题 | 每个 agent 按自己的兴趣写，章节之间没有共同的问题意识 | 产出是 N 份互不相干的笔记，不是一次研讨 |
| 无证据锚点 | “作者证明了 X”但没给页码、公式号、图号 | 无法核查，错误静默传播 |
| 无对抗 | agent 倾向复述作者，不会追问“这一步为什么成立”“哪里可能出错” | 把“读懂”伪装成“抄懂” |
| 译者/读者混淆 | 直接读中译本，把译本的偏差当成原文 |  translation error 被固化进研读笔记 |
| 无综合 | 没有论证图、没有一页纸、没有开放问题 | 读者仍然不知道这篇文章“到底做了什么” |
| 无溯源 | 没有记录谁在什么模型/提示词下写了哪一段 | 无法复现、无法更新、无法追责 |

所以，**“分章”只是分工，不是研讨**。研讨班需要额外的四件事：**共享地图、证据协议、对抗质询、综合成稿**。

## 2. 目标与非目标

### 2.1 目标

为每一篇入选文献产出一套 **seminar dossier（研读档案）**，至少包含：

1. `seminar.yaml`：元数据、底本、版权、角色、状态；
2. `map.yaml`：章节树、页映射、公式/图/表清单、依赖关系；
3. `reports/`：逐节研读报告（每人一块，结构化）；
4. `claims.jsonl`：断言-证据账本；
5. `questions.jsonl`：问题与质询账本；
6. `transcript.md`：研讨记录（两轮）；
7. `notes.md`：综合研读笔记；
8. `argument_graph.json` + 可视化：论证图；
9. `errata.md`：原文/译本疑点登记；
10. `glossary_delta.tsv`：术语与记号增量；
11. `one_pager.md`：一页纸总结；
12. `manifest.json`：模型、提示词、时间、哈希、版本。

最终形成：
- 一个可检索的**研读文库**；
- 一个可公开展示的**网站**（版权分层）；
- 一套可复用的**模板、脚本、质量闸门**；
- 一个能持续扩张的**研讨班生产流水线**。

### 2.2 非目标

- **不做“全文公开翻译站”**。版权不允许，且会把工程拖入法律风险。
- **不做“替代专家的自动综述”**。研讨班产出是**研读辅助**，不是同行评议结论；所有解释性断言必须标注置信度。
- **不做“一次性聊天”**。没有存档、没有证据链的对话不算研讨班。
- **不追求“篇篇都做”**。先做 5 篇高质量试点，验证流水线，再扩张。
- **不先搭大平台**。先做一篇的完整页面，再抽象成站点。

### 2.3 成功判据（可验证）

试点（JP11）结束时，必须同时满足：

- G0–G7 全部通过（见 §7）；
- 每个 section 至少 1 份研读报告，覆盖 100%；
- 99 条编号公式、9 幅图全部有归属与核对记录；
- `claims.jsonl` 至少 40 条，100% 有页码/公式锚点；
- 每个 section 至少 3 条质询，质询解决率 ≥80%，未解决的全部登记；
- 一页纸 ≤800 字，能让没读过原文的同行说出“这篇文章做了什么、怎么做的、哪里可疑”；
- 一位真实同行（你或你指定的专家）用 ≤2 小时抽查，给出 ≥80/100 的评分；
- 网站页面可打开、可搜索、可引用，且不含版权风险内容。

## 3. 研讨班是什么

### 3.1 定义

> **AI 研讨班**：围绕一篇文献，由多个承担不同角色的 agent（以及必要时的人类主班）按固定协议，先独立研读、再交叉质询、最后综合成稿的一次**有档案的生产过程**。

关键词是“角色”和“协议”，不是“多个 agent 聊天”。

### 3.2 与相邻活动的区别

| 活动 | 主要产出 | 与研讨班的区别 |
|---|---|---|
| 翻译 | 可信中文文本 | 只解决“说什么”，不解决“为什么/是否成立/与谁相关” |
| 读书会 | 口头讨论、零散笔记 | 无证据锚点、无结构化档案、无质量闸门 |
| 综述 | 面向领域的二手总结 | 研讨班面向**单篇**，强调逐节证据与质询，不追求覆盖全领域 |
| 论文精读笔记 | 个人笔记 | 研讨班是**多角色、可交叉复核、可发布**的工程产物 |

### 3.3 产物清单（dossier 十件套）

| # | 文件 | 作用 | 主要作者 |
|---|---|---|---|
| 1 | `seminar.yaml` | 元数据、底本、版权、角色、状态 | 主班 |
| 2 | `map.yaml` | 章节树、页映射、公式/图/表、依赖 | 主班 |
| 3 | `reports/*.md` | 逐节研读报告 | 讲读 |
| 4 | `claims.jsonl` | 断言-证据账本 | 讲读 + 质询 |
| 5 | `questions.jsonl` | 问题/质询账本 | 质询 + 全体 |
| 6 | `transcript.md` | 两轮研讨记录与裁决 | 记录 |
| 7 | `notes.md` | 综合研读笔记 | 综合 |
| 8 | `argument_graph.json` | 论证图（节点/边） | 综合 |
| 9 | `errata.md` | 原文/译本疑点 | 译校 |
| 10 | `one_pager.md` | 一页纸总结 | 综合 + 主班 |

外加 `glossary_delta.tsv`、`manifest.json`、`README.md`。

### 3.4 质量观：证据链而不是文采

研讨班不奖励“写得漂亮”，只奖励**可核查**。每一条实质性断言都要能回答：

- 出处在哪？（页码、公式号、图号、定理号）
- 是原文说的，还是你推断的？
- 如果是推断，依据是什么？置信度多少？
- 有没有反例、边界条件、被作者忽略的情形？
- 译本在这里是否忠实？页图上的符号是否与文字层一致？

## 4. 工程架构

### 4.1 总体流水线（S0–S8）

```
S0 立项        元数据、底本、版权、范围、角色、验收标准
S1 预处理      页图、文字层、公式/图/表清单、章节树、术语基线、页映射
S2 冷读与地图  主班读摘要/引言/结论，产出 map + 10 个种子问题 + 分工
S3 独立研读    各讲读只读自己那块，产出报告 + claims + questions（禁止互相看）
S4 交叉质询    互评 + 红队 + 译校三路核对，产出 challenge list
S5 研讨圆桌    两轮：澄清轮、质询轮；记录裁决
S6 综合        论证图、综合笔记、一页纸、开放问题、术语增量
S7 质检与发布  G0–G7、编译/构建、归档、网站条目
S8 复盘        指标、耗时、成本、经验回写模板
```

关键设计：**S3 必须独立**。如果讲读在写报告前就互相看，会迅速趋同，研讨班退化为“合写一份综述”。独立性靠写作用域和任务板保证。

### 4.2 角色与最小配置

| 角色 | 职责 | 25 页配置 | 50 页配置 | 100+ 页配置 |
|---|---|---|---|---|
| 主班 Chair | 地图、分工、裁决、终审、发布 | 1 | 1 | 1 |
| 讲读 Reader | 逐节研读、报告、claims | 2–3 | 3–4 | 5–8（或拆班） |
| 质询 Examiner | 红队、反例、缺口、逻辑攻击 | 1 | 1–2 | 2 |
| 译校 Textual Critic | 原文-页图-译本三路核对、errata | 1 | 1 | 1–2 |
| 综合 Synthesizer | 论证图、综合笔记、一页纸 | 1（可由 Chair 兼） | 1 | 1 |
| 编辑 Editor | schema、术语、引用、风格、版权 | 1（可由 Chair 兼） | 1 | 1 |
| 记录 Scribe | transcript、manifest、任务板 | 1（可由 Chair 兼） | 1 | 1 |

**最小可行配置**：Chair + 2 Readers + Examiner + Translator = 5 个角色；短文章可压到 3 个 agent（Chair 兼综合/编辑，Reader 兼记录）。

**角色分离的硬规则**：
- 写报告的人不能给自己的报告做终审；
- 质询人不能同时是同一节的讲读；
- 译校不参与“解释作者意图”的裁决，只负责文本忠实性；
- 主班对分歧有最终裁决权，但必须把双方理由写进 transcript。

### 4.4 任务板与写作用域

沿用你已有的多智能体规范，但把“翻译块”换成“研读块”：

- 每个任务在共享任务板上登记：owner、输入、输出、写作用域、验收标准、依赖；
- 写作用域互斥：`reports/r01_*.md`、`claims/r01.jsonl`、`challenges/x01_*.md` 各自独立；
- 主班独占 `map.yaml`、`seminar.yaml`、`notes.md`、`one_pager.md`、`manifest.json`；
- 任何跨文件修改必须先经主班，避免“顺手改别人报告”；
- 任务完成必须附：文件路径、证据数量、未决问题、自检结果。

### 4.5 上下文管理

这是多 agent 研讨班最容易翻车的地方。规则：

1. **每个 agent 只拿三样东西**：`map.yaml` 的相关片段、自己负责的页图/文字、术语表。不要给全文。
2. **地图是共享的，全文不是**。地图包含：章节树、每节的核心问题、关键定义、公式/图清单、前后依赖。
3. **报告是交接物**。S4 互评时，质询人读的是报告 + 对应页图，不是重读全文。
4. **摘要分层**：每份报告 ≤2500 字；每条 claim ≤120 字；每节最多 12 条 claim。
5. **超页数就拆班**：>60 页的文献拆成 2 个研讨班（或 2 个“半场”），不要用 8 个 agent 硬啃 150 页。

### 4.6 工具链

| 环节 | 工具 | 说明 |
|---|---|---|
| PDF 页图 | PyMuPDF | 150 dpi 全页 + 300–600 dpi 局部裁图 |
| 文字层 | PyMuPDF / pdftotext | 只用于定位，公式不可信 |
| 公式/图清单 | PyMuPDF + 正则 + 人工复核 | 生成 `equations.tsv`、`figures.tsv` |
| 页映射 | 脚本 + 首末页人工确认 | `page_map.tsv` |
| 术语 | TSV/CSV | 冻结后只增不改，改动留痕 |
| 校验 | Python 脚本 | schema、锚点、覆盖率、重复、缺号 |
| 构建 | Pandoc/LaTeX（可选） | dossier PDF；网站用 Astro |
| 版本 | Git | 每次研讨班一个 tag |

你机器上已有：Python（PyMuPDF）、MiKTeX（xelatex/latexmk）、Node/pnpm、git。无需新装重型依赖。

## 5. 协议（本计划的核心）

### 5.1 证据锚点协议

所有引用统一写成可解析的锚点：

```
[src p.12]            原文 PDF 第 12 页
[src p.12 l.3]        原文 PDF 第 12 页第 3 行（可选）
[eq 4.16]             编号公式 (4.16)
[fig 8.1]             图 8.1
[thm 8.2]             定理 8.2
[zh p.7]              译本第 7 页
[note n.3]            译者批注第 3 条
```

规则：
- 正文引用用 `[src p.N]`，不要只写“原文”。
- 公式必须同时给 `[eq x.y]` 与 `[src p.N]`；公式的最终真值是页图，不是文字层。
- 图必须给 `[fig x.y]` 与 `[src p.N]`。
- 译本引用只在“讨论翻译”时使用，不能替代原文证据。

### 5.2 断言-证据账本（claims.jsonl）

每行一条 JSON：

```json
{"id":"C-04-03","section":"4","claim":"格极化 K3 曲面的周期区域是 IV 型对称空间的有界对称域。","type":"theorem","source_anchor":"src p.6, eq 4.16","translation_anchor":"zh p.5","evidence":"原文定义 4.1 与 (4.16) 给出周期区域；有界性由 (4.18)–(4.20) 的管状区域描述。","status":"verified","confidence":"high","challenged_by":[],"resolution":"","notes":""}
```

字段约束：
- `type` ∈ `definition | theorem | proof-step | example | interpretation | connection | historical`
- `status` ∈ `proposed | verified | disputed | refuted`
- `confidence` ∈ `high | medium | low`
- `type=interpretation` 或 `connection` 必须显式标注，不能伪装成原文结论。
- 每节 claim 上限 12 条；超出的放入“次要断言”附录。

### 5.3 三路核对（原文 / 页图 / 译本）

对每一条涉及公式、符号、编号、定理陈述的 claim，做三路核对：

1. **文字层**：用于定位句子与段落；
2. **页图**：用于确认符号、上下标、花体、箭头、括号层级；
3. **译本**：用于对照中文表述是否等价。

任一路不一致：
- 不擅自修正原文；
- 写入 `errata.md`，标 `原文疑点 / 译本疑点 / 文字层陷阱`；
- 在 claim 的 `notes` 中注明“按页图/按原文/按译本”；
- 若影响理解，提交 S5 圆桌裁决。

### 5.4 质询协议（红队）

质询人不是“再写一份笔记”，而是**攻击**。每个 section 至少提出 3 条，类型必须覆盖：

- **澄清型**：这个定义里的“紧”“可微”“有限型”到底指什么？边界情形呢？
- **逻辑型**：这一步从 (4.12) 到 (4.13) 用了什么？作者说“显然”，真的显然吗？
- **反例型**：如果去掉某个条件，结论还成立吗？有没有低维反例？
- **连接型**：这个结论与另一篇文献的哪个定理是同一件事？哪个更强？
- **应用型**：这个构造能用来算一个具体例子吗？算出来是多少？

质询必须写成可回答的问题，附 `target_claim` 或 `target_section`；不能写“我觉得这里不对”这种不可操作的话。

### 5.5 分歧与裁决

- 讲读与质询不一致 → 记录双方理由 → 主班裁决；
- 裁决结果三选一：`accept`（质询成立，改 claim）、`reject`（质询不成立，保留 claim）、`open`（证据不足，挂起）；
- 所有 `open` 进入 `questions.jsonl` 的 `open` 状态，并在 `one_pager.md` 的“开放问题”中出现；
- 不允许“和稀泥”式修改：不能把有争议的断言改成模糊表述来回避。

### 5.6 术语与记号冻结

- 每篇研讨班开始时，从已有 `glossary.tsv` 继承基线，新增条目写入 `glossary_delta.tsv`；
- 术语一旦冻结，报告、笔记、网站统一使用；
- 记号表单独维护：符号、含义、首次出现、是否与原文一致；
- 发现原文记号冲突（如 JP11 的 `\mho`、`\varsigma`、`h^{2,Q}`），在 `errata.md` 登记，不在正文擅自统一。

### 5.7 交接协议

每个阶段结束时，主班在任务板写一条“交接摘要”，包含：

- 已完成什么、产物路径；
- 未决问题、下一步；
- 谁需要读什么；
- 哪些文件被修改（写作用域）；
- 自检结果（锚点数、claim 数、覆盖率）。

没有交接摘要的“完成”不算完成。

### 6.4 报告 frontmatter


正文固定五节：

1. **本节要解决什么问题**（≤200 字）
2. **定义与记号**（表格：符号/含义/首次出现/易错点）
3. **论证链**（按步骤，步步带锚点）
4. **例子与反例**（至少 1 个可计算/可检验的例子）
5. **疑点与问题**（≥3 条，链接到 questions）

### 6.5 `argument_graph.json`

```json
{
  "nodes": [
    {"id":"D4.1","type":"definition","label":"格极化 K3 曲面","anchor":"src p.6"},
    {"id":"T4.16","type":"theorem","label":"周期区域是有界对称域","anchor":"src p.6, eq 4.16"},
    {"id":"P8.2","type":"proof","label":"定理 8.2 的证明","anchor":"src p.19"}
  ],
  "edges": [
    {"from":"D4.1","to":"T4.16","relation":"uses"},
    {"from":"T4.16","to":"P8.2","relation":"used-by"}
  ]
}
```

`relation` ∈ `uses | proves | exemplifies | generalizes | contradicts | analogous | depends-on`。

### 6.6 `manifest.json`

记录：模型名/版本、提示词哈希、agent 角色、开始/结束时间、输入文件哈希、输出文件哈希、工具版本、评审人、变更日志。没有 manifest 的研讨班不能发布。

### 6.7 校验规则（自动化）

- schema 校验：YAML/JSON 必填字段；
- 锚点解析：所有 `[src p.N]`、`[eq x.y]`、`[fig x.y]` 必须能在 `map.yaml`/`page_map.tsv` 中找到；
- 覆盖率：每个 section 至少 1 份报告；每条公式/图至少被引用 1 次或标记 `skipped`；
- 编号连续：公式号、图号与原文清单一致（允许原书跳号，需登记）；
- 重复检测：claims 语义重复、报告段落重复；
- 术语一致性：同一术语不得有两种译法（除非登记）；
- 版权扫描：公开层不得出现超过阈值的原文/译文连续文本。

## 10. 网站：可行性、边界与 MVP

### 10.1 可行性判断

**技术上完全可行**：静态站、全文检索、数学公式、论证图、响应式前端，都是成熟方案；你机器上已有 Node/pnpm，部署到 Cloudflare Pages/Vercel 免费层即可。

**法律上必须分层**：

- 书籍译本（如深谷、植田、Kollár–Mori）：**不能公开全文**；公开的只能是你自己的导读、笔记、论证图、问题集、术语表，以及**短引用**（每段 ≤200 字，每节 ≤3 段，注明出处）；
- arXiv 论文：先看许可证。CC-BY 可以发布衍生译文（保留署名与许可证）；arXiv 默认许可证不允许无条件再发布，需逐篇确认；
- 出版社 PDF：不公开原文，不公开全文译文；只放元数据、链接、自己写的 notes；
- 网站必须提供版权说明、署名、联系/下架渠道。

**结论**：公开站做“**研读档案站**”，不是“翻译全文站”。这既规避风险，也更符合“研讨班”的定位：读者来看的是你的理解与问题，不是替代原书。

### 10.2 三层内容模型

| 层 | 内容 | 可见性 | 示例 |
|---|---|---|---|
| L0 公开 | 元数据、摘要（自己写）、一页纸、论证图、问题集、术语表、短引用 | 所有人 | 首页、seminar 详情 |
| L1 注册/私有 | 完整研读笔记、transcript、claims 全表 | 邀请/本地 | 研读档案全文 |
| L2 本地 | 原文 PDF、译本 PDF、页图 | 仅本地 | `source/` |

网站只构建 L0；L1 可作为“私有构建”或登录后内容；L2 永不进 Git/站点。

### 10.3 信息架构

```
/                         首页：文库概览、主题域、最新研讨班、方法说明
/seminars                 研讨班列表（筛选：主题/难度/状态/语言）
/seminars/<id>            详情：元数据、一页纸、章节地图、论证图、问题、errata
/seminars/<id>/notes      研读笔记（按节）
/seminars/<id>/claims     断言账本（可筛选 type/status）
/seminars/<id>/questions  问题与质询（可筛选 open/resolved）
/glossary                 术语与记号总表（跨文献）
/topics/<topic>           主题域聚合
/method                   研讨班方法与质量闸门
/about                    关于、版权、署名、下架
/search                   全文检索（Pagefind）
```

### 10.4 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 框架 | Astro + Content Collections | 静态优先、Markdown/YAML 友好、构建快 |
| 样式 | Tailwind CSS | 快速做出干净的学术排版 |
| 数学 | KaTeX | 静态渲染、速度快 |
| 搜索 | Pagefind | 纯静态、无需后端 |
| 图 | Cytoscape.js / D3 | 论证图交互；MVP 可先用静态 SVG |
| 内容 | Git + Markdown/YAML/JSONL | 可审阅、可 diff、可回滚 |
| 部署 | Cloudflare Pages | 免费、全球 CDN、预览部署 |
| 分析 | Plausible/Umami（可选） | 隐私友好；也可不加 |

### 10.5 MVP（建议先做这个）

**范围**：只做 JP11 一篇。

页面：
1. 首页：项目一句话、3 个统计（25 页/99 公式/9 图）、JP11 卡片、方法入口；
2. `/seminars/SEM-JP11`：元数据、一页纸、章节地图（8 节 + 4 小节）、论证图（静态 SVG）、3 条 claims、3 条 questions、2 条 errata；
3. `/seminars/SEM-JP11/notes/1`：§1 的样例研读笔记；
4. `/method`：方法与质量闸门；

**工期**：3–5 个工作日（含内容整理）。**成本**：域名约 ¥70–100/年；托管免费；总成本 <¥200/年。

**验收**：手机/桌面可读；Lighthouse 性能 ≥90；无版权风险文本；能被搜索引擎索引；页面可作为“研讨班产品”的样板给合作者看。

### 10.6 发布与运维

- 仓库：`AI研讨班工程` 单独 Git 仓库（不要把桌面其他工程混进来）；
- 分支：`main` 自动部署；PR 预览；
- 内容更新：新增 `seminars/<id>/` + `site/content` 映射；
- 备份：Git + 本地冷备；每月检查链接；
- 下架：`/about` 提供联系邮箱；收到权利方通知 48 小时内移除相关内容；
- 监控：Cloudflare Analytics；不做用户追踪。

### 10.7 不做什么

- 不做用户系统（MVP）；
- 不做评论/论坛；
- 不做全文 PDF 在线阅读；
- 不做付费墙；
- 不做“AI 自动问答”（除非有明确需求与审核机制）。

## 13. 决策点与下一步

### 13.1 决策点

- **D1（试点后）**：JP11 是否达到 80/100？达到则进入第一批，否则改协议再试一次。
- **D2（3 篇后）**：模板是否稳定？稳定则固化 v1.0，不再每篇改。
- **D3（5 篇后）**：网站是否公开 beta？公开则做版权审计与下架流程。
- **D4（10 篇后）**：是否启动专著系列？启动则按“章级研讨”排期。

### 13.2 立即要做的五件事

1. 批准本计划，确认 JP11 试点范围与角色；
2. 在 `seminars/SEM-JP11/` 下建立目录，跑 S1 预处理脚本；
3. 写 `seminar.yaml`、`map.yaml`，锁定 3 位 Reader 的分工；
4. 产出第一份样例报告（§1–§3），由你抽查，校准“什么叫合格”；
5. 用 JP11 的公开层内容做网站 MVP 的首页与详情页。

### 13.3 停止规则

出现以下任一情况，暂停扩张，回到试点：

- 连续 2 篇专家评分 <70；
- 单篇成本超过预算 2 倍；
- 公开层出现版权投诉；
- 3 份报告之间出现“互相复制”；
- 一页纸无法让同行说出“这篇文章的贡献与疑点”。
