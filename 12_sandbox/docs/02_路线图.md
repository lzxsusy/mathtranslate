# 路线图：90 天 + 12 个月

**原则**：先复现，再公开，再基线，再扩量。**不要先建 API。** 免费开放，不设付费墙。

## 一、90 天（v0.1 preview）

### W1–2 复现性（P0）

目标：陌生人 clone 后一条命令跑通。

- [ ] 在 `datasets/leanstmt/` 补 `lakefile.lean`、`lean-toolchain`、`lake-manifest.json`（从 `shuyi/formal/` 同步，钉死 Lean 4.36.0 + mathlib d33c49ca）。
- [ ] 加 `Dockerfile`（或 `docker/`）：干净镜像里 `lake build` + 40 卡验证。
- [ ] 加 GitHub Action：在干净 runner 上跑 `lake build`、`#print axioms`、40/40 校验；badge。
- [ ] 写 `docs/复现指南.md`：一条命令、常见错误、版本说明。
- [ ] 验收：一台没装过 Lean 的机器（或 CI runner）通过；40/40 与 `verification.jsonl` 一致。

### W3–6 公开 preview

目标：让外面的人能看见、能下载、能引用。

- [ ] HuggingFace 数据集：40 卡（statement + Lean + anchor + status + license），datasheet，英文 README。
- [ ] 静态 Gap Atlas：19 gap + 67 nLab DAG + 154 GLC 卡，按概念浏览，带页码锚。
- [ ] 仓库根 README 加一段「12_sandbox 是什么」，指向 `12_sandbox/README.md`。
- [ ] `docs/03_给大模型公司的一页说明.md` 定稿，放仓库根和站点。
- [ ] 验收：HF 上线；站点可浏览；license map 清楚；英文 README 可读。

### W7–10 基线

目标：知道这些题到底有多难，别人能不能复现。

- [ ] 3–5 个模型（GPT-6、Kimi、DeepSeek、Leanstral 等）跑 40 卡，记录 pass@1/5、编译错误、放弃。
- [ ] 3–5 位博士/高年级博士生做计时基线（每张卡限时，记录「卡在哪」）。
- [ ] 失败 taxonomy：缺定义 / 弱化陈述 / 编译错 / 方向错 / 放弃。
- [ ] 写 `docs/基线_v0.1.md`：表 + 观察 + 可复现命令。
- [ ] 验收：一张基线表；别人按文档能复现。

### W11–13 论文 + 社区

目标：建立优先级和可信度。

- [ ] 技术报告/workshop 论文：40 卡、21 certified、19 gap、基线、失败 taxonomy、页码锚方法。
- [ ] 投 math-AI / Lean / NLP 的 workshop；同时放 arXiv。
- [ ] 发 Lean Zulip、nLab、中文数学社区；找 2–3 个合作者。
- [ ] 验收：投稿；≥1 外部 PR/issue；≥1 合作意向。

### 如果 90 天没有外部信号

不硬冲 300。把范围缩到「40 卡 + 19 gap + Atlas」，把它当成个人/小团队的工具和语料；继续维护，但不做 benchmark 承诺。**免费项目不需要「增长」，需要「有人真的用」。**

## 二、12 个月（v0.2 → v1.0）

### v0.2（第 4–6 个月）：100 卡

- [ ] 从 1,676 张资料卡里选 100 条研究级陈述，分 full / skeleton / gap。
- [ ] 每条有页码锚、依赖、formalizable 状态、至少一个候选 Lean 形式化。
- [ ] 10–20 条 gap 写成 Gap Atlas 条目（缺失定义 + 建议签名 + 依赖）。
- [ ] HF v0.2 + DOI；changelog。
- [ ] 验收：100 条中 ≥80 条通过 schema 校验；≥30 条有编译器验证；Gap Atlas ≥20 条。

### v0.3（第 7–9 个月）：Judgment Dataset

- [ ] 200–500 条「陈述 + 候选形式化 + 判定 + 理由」。
- [ ] 判定分四类：忠实 / 弱化 / 错误 / 缺口；每条有证据（页码、编译器输出、人审记录）。
- [ ] 写「怎么用这份数据训练 judge/reward model」的说明。
- [ ] 验收：≥200 条；双人复核 ≥50 条；公开 datasheet。

### v1.0（第 10–12 个月）：窄口 Benchmark

- [ ] 300 条研究级陈述（几何朗兰兹/镜像对称/中文语境），full/skeleton/gap 分层。
- [ ] private held-out（不公开答案）；公开 leaderboard（静态 JSON + CI 更新）。
- [ ] 3 个以上基线；防作弊 harness（固定 statement、禁 axiom/sorry、查空泛）。
- [ ] 论文 + DOI + HF 数据集 + 静态站。
- [ ] 验收：≥3 个外部团队/个人跑过；≥1 篇论文引用；≥1 个外部 PR 合并。

## 四、风险与应对

| 风险 | 应对 |
|---|---|
| 复现性修不好 | 先只做 40 卡；Docker 钉死版本；CI 先行 |
| 影子卡被当研究级 | 分 `full` / `shadow`；headline 只用 full |
| 防作弊不足 | 固定 statement；`#print axioms`；空泛检查；ProofGate 式抽检 |
| 单人维护不动 | versioned release；找 2–3 合作者；不承诺 live service |
| 法律边界 | clean-room 导出；不打包译文；license map |
| benchmark 饱和 | private held-out；年度 refresh；窄口（几何朗兰兹/中文） |
| 没人用 | 先当个人工具/语料；不追增长；有人用是 bonus |

## 五、不要做

- 不要先建 Docker/API 集群（用 Lean4Web / HF Spaces / OpenReward）。
- 不要做通用 proof benchmark（miniF2F 已饱和）。
- 不要拼语料体量（AutoMathText 2.46T，拼不过）。
- 不要收费、不要付费墙、不要「专家服务」包装。
- 不要把译文原文打包进发布物。
