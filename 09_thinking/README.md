# 09_thinking · AI 思考链的筛选、审计与上传纪律

> 版本：v1.0（2026-11-20）
> 适用：本仓库全部译注工程、资料卡工程、形式化工程，以及为它们工作的所有 agent。
> 上游：`MEMORANDUM_01_论证精读与语料生产.md`；本文件只加约束，不放松上游。

## 0. 为什么需要这条纪律

2026-11-20 的 SY01-26 全书校对跑了一次 272 个 agent 的批量任务：

| 指标 | 数值 |
|---|---|
| 子会话 | 272 个（全部 delegationDepth=1） |
| reasoning 字符 | 39,521,214 |
| 最终 text 字符 | 17,641 |
| 模型调用 | 2,543 次 |
| 输出 token | 15,151,401 |
| 成本 | ¥113.93 |
| 产出 | 153 个单元校对 JSON、24 张资料卡、403 页校订版 PDF |

结论很直接：**答案只有 1.7 万字符，判断过程有 3,952 万字符。** 人不可能通读后者；
但后者才是“为什么这样译、为什么否决另一个方案、哪里曾经译错又改回来”的唯一载体。
不筛选、不上传，等于每做完一部书就把最贵的部分扔掉。

同时必须承认另一面：raw reasoning 里大量是重复、试探、走错路和无关上下文。
**全部上传 = 把噪音和隐私一起发布，且没人会看。** 所以本纪律的核心不是“多传”，
而是“机器初筛 + 人做最后决定 + 只传可复用的判断”。

## 1. 什么算一条“思考链”

一条链不是一段思维流水，也不是任务摘要。它必须能独立回答：

> 在当时的信息下，做了什么判断；否决了什么；凭什么；如果新证据出现，什么情况下翻案。

因此一条合格的链必须包含七段（缺一不可）：

1. **任务**：当时的输入、约束、成功标准（不是事后总结）。
2. **关键片段**：2–8 段原始 reasoning 的压缩摘录，保留决策发生时的语气与犹豫。
3. **决策与替代方案**：选了什么、否决了什么、否决理由。
4. **自纠与回退**：曾经错在哪里、怎么发现、改了什么。
5. **验证证据**：编译/测试/diff/核验记录，不能只有“我觉得对”。
6. **逆转条件**：什么证据会推翻这个决定。
7. **交付物**：被这个决定实际改变的文件、页码、行号。

**反例**（不算链）：整段 CoT 导出；“我检查了术语，没问题”；只有结论没有替代方案；
把 `04_playbook/08_论证精读与知识网络.md` 里的论文论证链 `chain.json` 混进来——
那是“论文的论证结构”，不是“agent 的判断过程”，两者可以互相引用，但不能互相替代。

## 2. 四层，各归其位

| 层 | 位置 | 内容 | 是否入库 | 保留 |
|---|---|---|---|---|
| **L0 raw** | `06_sessions_raw/`（Release 附件） | 全量会话事件，脱敏后 zstd | 否（Release） | 长期 |
| **L1 候选卡** | `.thinking_candidates/cards/`（本地，gitignore） | 机器初筛的 ≤9KB 压缩卡，含评分/理由/审计问题 | **永不入库** | 审计后 30 天可删 |
| **L2 批准链** | `09_thinking/chains/<项目>/` | 人批准、脱敏、≤12KB 的正式链 | 是 | 永久 |
| **L3 审计报告** | `09_thinking/audit/` | 季度/批次覆盖、批准率、翻案率 | 是 | 永久 |

机器只负责 L0→L1；人负责 L1→L2；L3 由项目负责人每季度汇总。
**任何 agent 不得直接把 L0 写进 L2，也不得自己批准自己生成的卡。**

## 3. 硬纪律（R1–R12）

**R1 分层强制。** raw reasoning 只能留在 L0/L1；仓库里出现未压缩的 reasoning 原文，
按发布事故处理，`check` 直接失败。

**R2 一条链只回答一组决策。** 默认一会话一链；若一个会话里有两个互不相干的决策族，
拆成两条，不要做“大杂烩”。

**R3 七段齐全。** 第 1 节列出的七段缺一不可；`approve` 会拒收缺段卡片。
链文件 ≤12KB；单条引用 ≤200 字；不引底本长段。

**R4 必须有否决方案与逆转条件。** 只写“我选了 A”不算链；必须写“为什么不是 B”和
“什么证据会让我改回 B”。这一条是链与“成功学总结”的分界线。

**R5 可追溯。** front matter 至少含 `chain_id / project / session / created / approved_by /
approved_at / score / reasoning_chars / audit_note / source_card`。会话 id 必须能在
`06_sessions_raw` 或本机会话库中定位。

**R6 人工批准。** `approve --auditor <真人名>`；生成 agent 不得自批，也不得代替人写
“审计结论”。审计人必须在卡片第 0 节写一句理由，指出“哪个决定改变了交付物”。

**R7 脱敏。** 路径、邮箱、令牌、账号、底本扫描件路径一律处理；`approve` 会跑
`scrub()`，但审计人仍要目检。第三方译文/原文引用不超过 200 字，且只引与判断直接相关的句子。

**R8 发布闸门。** 新交付或新版本打 tag 前，`python tools/thinking_audit.py check
--require-coverage` 必须通过；缺链时不得发布。现有存量按 §5 的时间表补。

**R9 覆盖目标。** 新交付：100% 至少 1 条链。存量 95 部：2027-Q1 末 ≥60%，2027-Q2 末 100%。
每部 1–3 条，不追求条数。

**R10 索引唯一。** `09_thinking/index.csv` 是唯一登记表；链文件与索引必须一一对应。
`check` 同时校验：文件存在、七段齐全、≤12KB、索引无孤儿。

**R11 质量优先。** 同一决策不重复上传；同一项目同一术语决定只保留最早、最完整的一条；
“我检查了一遍”不算链。候选→批准率控制在 10–20%，批准率过高说明初筛太松。

**R12 季度复盘。** 每季度写 `09_thinking/audit/YYYY-QN.md`：候选数、批准数、被引用次数、
后来被翻案的链数。翻案率 >20% 时，先改初筛规则，不要先怪审计人。

## 4. 工作流（人机分工）

```bash
# 1) 机器初筛：扫一个父会话（或最近 N 天），每项目最多 3 张候选卡
python tools/thinking_audit.py scan \
  --root session-c054c128-724d-4e96-9e1f-e055ce62c51a \
  --per-project 3 --cards 15

# 2) 人只看排名前 10–20；每张卡第 0 节写“上传/不上传/改写”，并回答第 9 节五问
python tools/thinking_audit.py rank --top 15

# 3) 批准：写入 09_thinking/chains/<项目>/ 并登记 index.csv
python tools/thinking_audit.py approve \
  --card .thinking_candidates/cards/SY01-26_5e29f91b.md \
  --auditor 李泽轩 \
  --note "unit 64 的 issue 取舍与 skipped 判断改变了校对 JSON"

# 4) 闸门
python tools/thinking_audit.py check --require-coverage
python tools/thinking_audit.py coverage
```

**时间盒**：每卷审计 15 分钟，只看 top 3；每月一次批量（1 小时）处理跨项目候选。
人不需要读 raw reasoning；只有对某张卡存疑时，才用
`python tools/thinking_audit.py extract --session <id>` 看单会话全文。

## 5. 存量补链时间表

| 时间 | 范围 | 目标 |
|---|---|---|
| 2026-11-20 起 | 所有**新**交付/新版本 | 100% 至少 1 条链，`check --require-coverage` 通过 |
| 2026-12-31 | 2026-Q4 交付的 20 部 | 每部 ≥1 条 |
| 2027-03-31 | 存量 95 部 | ≥60%（≥57 部） |
| 2027-06-30 | 存量 95 部 | 100% |

补链顺序：先补“有明确术语/结构争议”的卷（SY01-26、SY02-09、SY07-08、SY05-25），
再补纯翻译卷；资料卡与形式化工程按“每 20 条记录 1 条链”折算。

## 6. 角色

| 角色 | 职责 | 不可以做 |
|---|---|---|
| 生成 agent | 跑 `scan`，写候选卡；在卡里保留原始会话 id | 自批、改 `decision`、写“审计结论” |
| 审计人（人） | 看 top 卡，写理由，跑 `approve`；对脱敏负责 | 批量无差别点“通过” |
| 项目负责人 | 季度 `check`、写 L3 报告、维护 index | 用链数量当 KPI |
| 发布脚本 | tag 前跑 `check --require-coverage` | 跳过失败项 |

## 7. 指标与反模式

**看四个指标，不看链数量：**

- 候选→批准率（目标 10–20%）；
- 批准链被后续工作引用/复用的次数（README、论文、新会话）；
- 决策翻案率（目标 <20%）；
- 已发布卷覆盖率（§5）。

**反模式：**

- 把 raw CoT 倒进 git（体积、隐私、噪音三输）；
- 让生成 agent 自己批准；
- 只写“结论正确”，不写被否决的方案；
- 把论文 `chain.json` 当 agent 思考链；
- 为了覆盖率凑数，一条链复制到多个项目；
- 用“上传了多少 MB”衡量质量。

## 8. 与现有资产的关系

| 资产 | 回答的问题 | 与思考链的关系 |
|---|---|---|
| `02_trajectories/` | 做了什么（工具调用序列） | 链引用轨迹；轨迹不替代链 |
| `06_sessions_raw/` | 原始证据是什么 | L0；链是它的压缩与判断层 |
| `04_playbook/08_论证精读与知识网络.md` | 论文的论证结构 | 论文链；可与 agent 链互链，不混用 |
| `datasets/math/` | 数学命题与证明步骤 | 链里的“决策/验证”可转成训练样本 |
| `formal/`（规划中） | 形式化陈述与证明 | 形式化决策（选哪个陈述、为什么加假设）优先入链 |

## 9. 红线

1. 不上传未脱敏的路径、邮箱、令牌、账号。
2. 不上传底本扫描件、OCR 全文、第三方译文长段（>200 字）。
3. 不上传未经人批准的链；不把“机器评分”当批准。
4. 不用链替代 `RELEASE_REGISTER.csv` 的权利登记；权利状态仍以台账为准。
5. 发现链内容与交付物不符时，先改链或撤链，再发布。

---

**一句话**：raw 留在 L0，机器把 3,952 万字符压成 20 张卡，人只批其中 2–3 条，
仓库里只留“判断 + 否决 + 证据 + 逆转条件”。这就是本纪律的全部。
